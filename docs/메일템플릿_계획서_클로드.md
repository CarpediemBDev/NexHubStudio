# B2B 메일 템플릿 관리 시스템 구축 계획서 (Claude)

> **문서 목적**: 다른 프로젝트에서 개발자 또는 AI 에이전트에게 메일 템플릿 관리 시스템을 지시할 때
> 그대로 복사해 쓸 수 있는 표준 지침서. **"무엇이 있는가"가 아니라 "런타임에 어떻게 도는가"** 를 기준으로 기술한다.
>
> **현재 구현 범위**: DDL 3종 + 관리 화면 3종(목데이터). DB/백엔드 연동은 미착수.

## 1. 아키텍처 결론

### 💡 "문법은 Velocity(`.vm`), 저장소는 DB(CLOB)"

템플릿 본문은 **디스크의 `.vm` 파일이 아니라 `MAIL_TEMPLATE_VERSION.BODY_HTML` (CLOB/LONGTEXT) 컬럼**에
Velocity 문법이 포함된 HTML 문자열로 저장한다. 런타임에는 파일 로더가 아니라 **문자열 로더**로 머지한다.

#### 세 방식 비교

| 항목 | 순수 HTML + `replace()` | `.vm` 파일 (classpath) | **DB 저장 + Velocity 문법 (채택)** |
|---|---|---|---|
| 변수 치환 `${userName}` | O | O | O |
| 반복 (주문 상품 N건) | **X** | O | O |
| 조건 (할인 있을 때만 노출) | **X** | O | O |
| 운영자가 화면에서 수정 | O | **X (재배포)** | O |
| 다중 WAS 동기화 | - | **X** | O |
| 버전/롤백 | 직접 구현 | git only | O (VERSION 테이블) |
| 형상관리(코드리뷰) | X | O | O (seed `.vm` 파일 병행) |

#### 왜 디스크에 파일을 쓰지 않는가 — 실무에서 터지는 순서

1. **다중 WAS 동기화 불가** — WAS 1호기에서 화면으로 파일을 써도 2·3호기 디스크엔 없다.
   L4가 2호기로 붙이는 순간 템플릿 없음 에러 또는 구버전 발송. NFS로 공유하면 NFS가 SPOF가 된다.
2. **무중단 실시간 반영** — DB면 `CURRENT_VERSION_ID` UPDATE 한 줄로 전 서버 즉시 반영. 재배포·재기동 없음.
3. **원클릭 롤백** — 파일은 덮어쓰면 끝. DB는 버전 행이 쌓이므로 v3 → v2 되돌리기가 UPDATE 한 줄.
4. **사후 재현성 (감사 요건)** — 발송 로그에 `TEMPLATE_ID` 가 아니라 **`VERSION_ID`** 를 남긴다.
   "3월 5일에 나간 그 메일"의 원문을 그대로 재현할 수 있다. 파일 방식은 이미 덮어써져서 불가능.
5. **컨테이너 재기동 시 소실** — K8s/Docker 환경에서 로컬에 쓴 `.vm` 은 파드 재시작마다 날아간다.

#### 그래도 `.vm` 파일을 병행하는 이유

초기 기본 템플릿만 `backend/src/main/resources/templates/mail/*.vm` 로 두고
**부팅 시 DB에 없으면 seed(insert), 있으면 skip**. 개발자는 파일로 코드리뷰하고, 운영자는 화면에서 고친다.
운영 중 수정본은 DB에만 쌓이고 파일은 건드리지 않는다.

> 참고: 본 프로젝트(NexHubStudio)에는 이미 실제 `.vm` 4개가 있다 —
> `feature/fullstack-migration` 브랜치 `backend/src/main/resources/templates/mail/`
> (설비지원 / 고장수리 / 개조개선 / 셋업해제). 단, Velocity 의존성과 MailService 는 아직 없다.

## 1.5 B2B 메일은 "확인"이 아니라 "확인 + 즉시 처리"다

이 설계에서 가장 중요한 화면 요구사항이다.

| | B2C 메일 | **B2B 업무 메일** |
|---|---|---|
| 목적 | 알림·확인 (주문확인, 배송안내) | **알림 + 업무 수행** |
| 받는 사람이 할 일 | 읽고 끝 | 결재하고, 접수하고, 조치해야 함 |
| 메일의 성패 | 열람률 | **클릭 → 처리 완료율** |

따라서 모든 업무 메일은 아래 3단 구성을 강제한다.

```
1) 무슨 일인지 한 줄        제목 + 첫 문단
2) 판단에 필요한 요약 정보  표 (문서번호 / 설비명 / 기한 / 요청자)
3) 바로 처리하는 CTA 버튼   시스템 해당 화면으로 딥링크   ← 이게 핵심
   + 보조 링크             (미리보기 / 목록 / 반려)
```

### 딥링크 규칙

```
${baseUrl}/{실제 라우터 경로}?{업무 식별자}&action={수행할 동작}&from=mail
```

예) `https://nexhub.example.com/work-group/request-workflow?requestNo=REQ-2026-0451&action=accept&from=mail`

- **실제 라우터 경로를 그대로 쓴다.** 별도 리다이렉트 페이지를 두면 링크가 먼저 썩는다.
- `action=` 파라미터로 화면 진입 즉시 처리 모드를 연다 (접수/승인/반려/작업시작).
- `from=mail` 로 유입 경로를 남겨 "메일 보고 실제로 처리했는가"를 측정한다.
- 미로그인 상태면 로그인 후 원래 URL 로 복귀시킨다(redirect 파라미터).
- 변수명은 `actionUrl` 로 통일하고 `MAIL_TEMPLATE_VAR.DATA_TYPE='URL'`, `REQUIRED_YN='Y'` 로 정의한다.
  → 링크 없는 액션 메일이 발송되는 사고를 스키마 수준에서 막는다.

### CTA 버튼 마크업 — Outlook 이 기준이다

버튼 디자인은 **Outlook(Word 렌더링 엔진)에서 무엇이 죽는가**로 결정된다.

| CSS | Outlook 데스크톱 | 대응 |
|---|---|---|
| `border-radius` | **무시 → 각진 사각형** | VML `v:roundrect` 폴백 |
| `box-shadow` | 무시 | 쓰지 않고 1px `border` 로 입체감 |
| `padding` on `<a>` | 클릭 영역이 글자 폭으로 축소 | VML 고정 높이/폭 |
| `@media` | 무시 (데스크톱은 넓으니 무해) | 모바일 전용으로만 사용 |
| 다크모드 자동 반전 | 흰 글자가 사라질 수 있음 | 배경·글자색을 **둘 다** 인라인으로 명시 |

그래서 버튼 하나를 **VML + 일반 마크업 두 벌**로 낸다. 조건부 주석이라 서로 배타적으로 렌더된다.

```html
<!--[if mso]>
<v:roundrect xmlns:v="urn:schemas-microsoft-com:vml" xmlns:w="urn:schemas-microsoft-com:office:word"
  href="${actionUrl}" style="height:46px;v-text-anchor:middle;width:176px;" arcsize="13%"
  strokecolor="#1d4ed8" fillcolor="#2563eb">
  <w:anchorlock/>
  <center style="color:#ffffff;font-family:'Malgun Gothic',sans-serif;font-size:14px;font-weight:bold;">결재하러 가기</center>
</v:roundrect>
<![endif]-->
<!--[if !mso]><!-- -->
<a class="cta-btn" href="${actionUrl}" style="display:inline-block;box-sizing:border-box;
   min-width:176px;padding:14px 26px;background:#2563eb;border:1px solid #1d4ed8;
   border-radius:8px;color:#ffffff !important;font-size:14px;font-weight:700;line-height:18px;
   mso-line-height-rule:exactly;text-align:center;text-decoration:none;letter-spacing:-0.2px;">결재하러 가기 &rarr;</a>
<!--<![endif]-->
```

- VML 은 폭을 px 로 고정해야 하므로 라벨 길이로 계산한다 — `max(176, 공백제외 글자수 × 15 + 74)`.
- `<w:anchorlock/>` 이 없으면 Outlook 에서 버튼 글자가 편집 가능해진다.
- `mso-line-height-rule:exactly` 가 없으면 Outlook 이 줄높이를 제멋대로 키운다.

#### `!important` 는 미디어쿼리에서만 쓴다

메일 HTML 이라고 `!important` 를 습관적으로 붙이면 안 된다. 필요한 곳은 한 군데뿐이다.

| 위치 | 필요한가 | 이유 |
|---|---|---|
| 인라인 `style="color:#fff"` | **불필요** | 인라인 선언은 이미 일반 author 규칙을 이긴다 |
| `<style>` 의 `.cta-btn{color:#fff !important}` | **쓰면 안 됨** | primary 에겐 중복이고, 같은 클래스를 쓰는 **ghost 버튼까지 흰 글자로 만든다** |
| `@media` 안의 `display/width` | **필수** | `<style>` 규칙이 인라인 `display:inline-block` / `min-width` 를 이기는 유일한 수단 |

두 번째 항목은 실제로 밟은 지뢰다. 인라인에도 `!important` 가 있어서 우연히 살아남았을 뿐인데
(`!important` 끼리 붙으면 인라인이 이긴다), 나중에 누가 인라인 쪽을 정리하면 **흰 글자 · 흰 배경**이 된다.
버튼 색은 인라인에만 두고 `<style>` 에서는 건드리지 않는다.

### 주 액션 + 보조 액션은 고스트 버튼으로

보조 링크를 본문 아래 작은 글씨 `<a>` 로 두면 눌리지 않는다.
**주 버튼(색 채움) + 보조 버튼(테두리만)** 을 나란히 두어 위계는 유지하되 클릭 가능하게 만든다.

| 톤 | 배경 / 테두리 | 용도 |
|---|---|---|
| `primary` | `#2563eb` / `#1d4ed8` | 결재·접수·승인 등 기본 처리 |
| `danger` | `#dc2626` / `#b91c1c` | 지연 독촉, 설비 경고, 비밀번호 재설정 |
| `success` | `#16a34a` / `#15803d` | 완료 확인 |
| `ghost` | `#ffffff` / `#cbd5e1` | 보조 액션 (미리보기 · 목록 · 반려) |

적용 예 — 결재 요청은 `[결재하러 가기 →] [문서 미리보기]`, 담당자 배정은 `[작업 시작하기 →] [배정 반려]`,
설비 이상 경고는 `[모니터링 화면 확인 →](danger) [지원 요청 등록]`.
보조 버튼에는 화살표를 붙이지 않아 시선이 주 버튼으로 가게 한다.

### 모바일에서는 세로로 쌓고 폭을 채운다

가로 배치 2버튼은 375px 에서 좁아져 오탭이 난다. 레이아웃의 `BASE_CSS` 에 넣는다.

```css
@media only screen and (max-width:480px){
  .cta-table{ width:100% !important; }                         /* 테이블이 shrink-to-fit 이라 이게 없으면 안 늘어난다 */
  .cta-cell { display:block !important; width:100% !important; }
  .cta-gap  { display:block !important; height:8px; width:100% !important; }
  .cta-btn  { display:block !important; width:100% !important; min-width:0 !important; }
}
```

`.cta-table{width:100%}` 을 빼먹으면 셀과 버튼에 `width:100%` 를 줘도 부모 테이블이 글자 폭만큼만
잡혀 버튼이 안 늘어난다. 실제로 이 순서로 한 번 틀렸다.

버튼이 아예 차단되는 클라이언트를 위해 **푸터에 `${actionUrl}` 원문을 함께 노출**한다(레이아웃에 포함).

### 레거시 `.vm` 자산 4종은 원문 그대로 등록한다

이 프로젝트에는 설비 업무용 `.vm` 이 이미 4개 있었다
(`equipment-support` / `failure-repair` / `modification-improvement` / `setup-release`).
새로 지어내지 말고 **원문을 그대로 템플릿으로 등록**하는 것이 이관의 출발점이다.

| 신규 템플릿 | 레거시 `.vm` 템플릿 |
|---|---|
| 평면 변수 `${userName}` | **객체 하나** `${formData.xxx}` + 별도 목록 변수 |
| 공통 레이아웃 사용 (`LAYOUT_ID=1`) | **완결형 문서** — `<style>` 자체 보유, `LAYOUT_ID=NULL` |
| CTA 딥링크 필수 | 결과 보고서라 CTA 없음 (승인/반려 상태를 본문에 표기) |
| 요약 표 1개 | 요청·접수·결과·진행내역 등 표 2~4개 |

이관 시 손댄 것은 `<html>/<head>/<body>` 래퍼를 벗기고 `<style>` + 본문을 이어 붙인 것뿐이다.
Velocity 문법은 한 글자도 바꾸지 않았다. `LAYOUT_ID` 를 `NULL` 로 두면
`composeMailHtml` 이 헤더/푸터를 붙이지 않으므로 원문이 그대로 렌더된다.

레거시 이관에서 실제로 걸린 문법 두 가지 — 신규 프로젝트의 렌더러도 지원해야 한다:

```velocity
#if($formData.files && $formData.files.size() > 0)   ← && 와 .size()
${formData.measureDetails.get($measure)}             ← Velocity Map 접근 .get()
```

> 자동 변환기: `scratchpad/gen-equip-templates.mjs` → `src/data/mailEquipmentTemplates.js`
> (`.vm` 원문을 읽어 목데이터로 변환. `.vm` 이 바뀌면 다시 돌리면 된다)

### "누구에게 보낼지"도 DB 에 있어야 한다

템플릿만 DB 로 빼고 수신자 결정을 자바 코드에 두면 무중단 교체가 반쪽이 된다.
**B2B 에서는 문구보다 수신자 규칙이 더 자주 바뀐다** — "이제 팀장도 CC 넣어줘" 한마디에 재배포가 필요해진다.

`MAIL_EVENT_RECIPIENT` 가 이벤트별로 TO/CC/BCC 규칙을 갖는다.

| RECIPIENT_TYPE | 해석 | TARGET_VALUE |
|---|---|---|
| `REQUESTER` | 의뢰자/기안자 | - |
| `ASSIGNEE` | 배정 담당자 | - |
| `APPROVER` | 결재선의 다음 차례 | - |
| `DEPT_HEAD` | 대상자 부서장 | - |
| `TEAM` | 부서 전체 | 부서코드 |
| `ROLE` | 역할 보유자 | 역할코드 (예: `EQUIP_MANAGER`) |
| `FIXED` | 고정 주소 | 이메일 (콤마 구분) |
| `EXPRESSION` | 모델 표현식 | `${order.manager.email}` |

`CONDITION_EXPR` 로 조건부 수신도 된다 — 예: 결재 요청에서 `urgency == '긴급'` 일 때만 부서장 CC.

발송 호출부는 수신자를 넘기지 않는다:

```java
mailService.send("REQUEST.ASSIGNED", model);   // 수신자는 DB 규칙이 결정
```

## 2. 런타임 시퀀스 — 이 문서의 핵심

### 2.1 [저장] 버튼을 눌렀을 때

저장 경로는 **두 갈래**다. 섞어서 한 엔드포인트로 처리하면 이름만 고쳐도 버전이 하나 늘어난다.

| 바뀐 것 | 대상 | 엔드포인트 | 버전 |
|---|---|---|---|
| 메타 (이름·코드·카테고리·엔진·상태·설명) | `MAIL_TEMPLATE` UPDATE | `PUT /api/mail/templates/{id}` | 증가 안 함 |
| 본문 (제목·프리헤더·HTML·TEXT) | `MAIL_TEMPLATE_VERSION` INSERT | `POST /api/mail/templates/{id}/versions` | +1 |

둘 다 바뀌었으면 둘 다 수행하며, **변경 사유는 본문이 바뀐 경우에만 필수**다.
검증 실패 시 어느 쪽도 반영하지 않는다(부분 저장 금지).

`TEMPLATE_CODE` 는 `MAIL_EVENT_TEMPLATE` 가 참조하는 업무 키이므로 **`DRAFT` 상태에서만 수정 허용**한다.
운영 중(ACTIVE)에 코드를 바꾸면 매핑이 끊겨 발송이 중단된다.

```
[저장 클릭] (engineType: VELOCITY)
   │
   ├─ 변경 사유 미입력 → 토스트 경고, [편집] 탭으로 포커스 이동, 중단
   ▼
1. POST /api/mail/templates/{templateId}/versions
   { subject, preheader, bodyHtml, bodyText, changeNote }
   ※ POST /api/mail/templates 는 "새 템플릿 생성"이라 엔드포인트가 다르다
   ▼
2. 서버 전처리
   - sanitize: <script>, on*=, javascript: 제거 (본문이 HTML 이므로 필수)
   - BODY_CHECKSUM = SHA-256(bodyHtml)
   - 직전 버전과 체크섬이 같으면 INSERT 생략 (의미 없는 버전 증가 방지)
   ▼
3. INSERT INTO MAIL_TEMPLATE_VERSION
     TEMPLATE_ID = 3
     VERSION_NO  = 4                 ← INT (1,2,3…). '1.1' 같은 소수 문자열 아님
                                        UNIQUE(TEMPLATE_ID, VERSION_NO) 제약
     ENGINE_TYPE = 'VELOCITY'
     BODY_HTML   = '<p>${userName} 님 반갑습니다</p>…'   ← CLOB
     STATUS_CODE = 'ACTIVE'
     CHANGE_NOTE = '문구 수정'
   ▼
4. UPDATE MAIL_TEMPLATE_VERSION SET STATUS_CODE='ARCHIVED' WHERE VERSION_ID = (직전 활성)
   UPDATE MAIL_TEMPLATE        SET CURRENT_VERSION_ID = (신규 VERSION_ID)
   ↑ 이 한 줄이 실제 "교체" 시점. 여기까지가 하나의 트랜잭션.
   ▼
5. 화면은 GET /api/mail/templates/{id} 재조회 → 헤더 배지 v3 → v4 갱신
```

**현재 목데이터 구현** ([MailTemplatePage.vue](../src/pages/mail/MailTemplatePage.vue) `save()` → `appendVersion()`)은
1~4단계를 메모리 배열 조작으로 대체한다. `versionNo = max(기존) + 1`, 직전 버전 `ARCHIVED` 표시,
`currentVersionId` 교체까지 동일한 상태 전이를 흉내내므로 API 호출로만 바꿔 끼우면 된다.

### 2.2 실제 메일이 발송될 때

```
[업무 로직]  mailService.send("REQUEST.ASSIGNED", model)
   │            ※ 수신자를 넘기지 않는다. 규칙이 DB 에 있기 때문.
   ▼
1. MAIL_EVENT_TEMPLATE 조회
   WHERE EVENT_CODE='ORDER.CONFIRM' AND ACTIVE_YN='Y'
     AND LOCALE_CODE=? AND BRAND_CODE=?
     AND (VALID_FROM_DT IS NULL OR VALID_FROM_DT <= NOW())
     AND (VALID_TO_DT   IS NULL OR VALID_TO_DT   >= NOW())
   → templateId 결정   ※ "어떤 메일이 어떤 템플릿으로 나가는가"의 단일 진실
   │  매핑이 없으면 → 발송 중단 + 로그(UNMAPPED). 코드 수정 없이 화면에서 붙이면 복구됨
   ▼
2. MAIL_TEMPLATE.CURRENT_VERSION_ID → MAIL_TEMPLATE_VERSION 로드
   (SUBJECT / BODY_HTML / BODY_TEXT / ENGINE_TYPE)
   ▼
3. 수신자 결정   ★ MAIL_EVENT_RECIPIENT
   WHERE EVENT_ID=? AND USE_YN='Y' ORDER BY SORT_ORDER
   각 규칙을 유형별로 해석해 TO/CC/BCC 주소 목록을 만든다
     REQUESTER  -> model.requester.email
     ASSIGNEE   -> model.assignee.email
     APPROVER   -> 결재선의 다음 차례 조회
     DEPT_HEAD  -> 조직도에서 부서장 조회
     TEAM/ROLE  -> 부서코드/역할코드로 사용자 조회
     FIXED      -> TARGET_VALUE 그대로
     EXPRESSION -> 모델 표현식 평가
   CONDITION_EXPR 이 있으면 참일 때만 포함 (예: 긴급 문서만 부서장 CC)
   │  TO 가 비면 → 발송 중단 + 로그(NO_RECIPIENT)
   ▼
4. 필수 변수 검증
   MAIL_TEMPLATE_VAR WHERE REQUIRED_YN='Y' 인데 model 에 키가 없으면
   → 발송 중단 + MAIL_SEND_LOG(STATUS='FAILED', ERROR_CODE='VAR_MISSING')
   ※ 깨진 메일을 보내는 것보다 안 보내는 게 낫다
   ▼
5. 레이아웃 결합
   MAIL_TEMPLATE_LAYOUT.HEADER_HTML + BODY_HTML + FOOTER_HTML (+ BASE_CSS)
   ▼
6. 엔진 머지 (ENGINE_TYPE 으로 분기) → subject / html / text 완성
   ▼
7. CSS 인라이너 적용 (Outlook 대응) → MimeMessage 조립
   multipart/alternative (text + html) + inline CID 이미지
   ▼
8. SMTP 발송
   ▼
9. INSERT INTO MAIL_SEND_LOG
     VERSION_ID      = 401          ← TEMPLATE_ID 가 아니라 VERSION_ID (재현성)
     MERGE_DATA_JSON = {…}          ← 치환에 쓴 모델 원본
     SUBJECT_SNAP    = '치환 완료된 제목'
     STATUS_CODE     = 'SENT' / 'FAILED' / 'BOUNCED'
```

### 2.3 테스트 발송

```
[테스트 발송 클릭]
   ▼
1. MAIL_TEMPLATE_VAR 로 입력 폼 자동 생성, SAMPLE_VALUE 프리필
   ▼
2. 입력값 변경 → POST /api/mail/templates/{id}/preview  { model }
   → { subject, html, text } 응답을 iframe srcdoc 에 주입 (저장 없이 렌더만)
   ▼
3. 수신자 검증: 사내 도메인 화이트리스트 (운영 데이터로 외부 대량발송 방지)
   필수 변수 누락 검증
   ▼
4. POST /api/mail/templates/{id}/test-send
   → MAIL_SEND_LOG 에 SEND_TYPE='TEST' 로 동일 적재 (테이블 분리하지 않음)
```

### 2.4 롤백

```
[버전] 탭 → v2 [되돌리기]
   ▼
POST /api/mail/templates/{id}/versions/{versionId}/activate
   ▼
UPDATE MAIL_TEMPLATE_VERSION SET STATUS_CODE='ARCHIVED' WHERE VERSION_ID=(현재)
UPDATE MAIL_TEMPLATE_VERSION SET STATUS_CODE='ACTIVE'   WHERE VERSION_ID=(대상)
UPDATE MAIL_TEMPLATE SET CURRENT_VERSION_ID=(대상)
   ▼
전 WAS 즉시 반영. 배포·재기동 없음. 이미 나간 메일의 로그는 옛 VERSION_ID 를 그대로 가리킨다.
```

### 2.5 [보기] 와 [되돌리기] 는 다른 동작이다

버전 목록의 두 버튼을 혼동하면 사고가 난다.

| 버튼 | 동작 | DB | 편집 중인 내용 |
|---|---|---|---|
| **[보기]** | 해당 버전을 **읽기 전용**으로 미리보기 | 변경 없음 | 보존됨 |
| **[되돌리기]** | 그 버전을 활성으로 교체 (§2.4) | `CURRENT_VERSION_ID` UPDATE | 현재 버전 내용으로 재로드 |

`[보기]` 구현 시 **편집 draft 를 덮어쓰면 안 된다.** 덮어쓰면
① 현재 버전으로 돌아올 방법이 없고 ② 화면이 dirty 상태가 되어
**실수로 [저장] 을 누르면 옛 버전이 새 버전으로 INSERT 된다.**

올바른 구조는 열람 상태를 별도로 두는 것이다:

```
viewingVersionId = null   → 편집 중인 draft 를 미리보기
viewingVersionId = 101    → v1 을 읽기 전용으로 미리보기 (draft 는 그대로)

[보기] 클릭       → viewingVersionId = 대상 (현재 버전이면 null)
[현재 버전으로]   → viewingVersionId = null
[편집] 탭 진입    → viewingVersionId = null   (편집은 항상 현재 버전 기준)
템플릿 전환       → viewingVersionId = null
```

열람 중에는 상단에 `v1 열람 중 (읽기 전용) · [현재 버전으로]` 배너를 띄워
지금 보는 것이 과거 버전임을 분명히 한다. 과거 버전을 몇 번이고 오갈 수 있고,
편집하던 내용은 그대로 남는다.

## 4. 화면 구조

3개 화면으로 분리한다. 권한 체계가 다르기 때문이다 —
템플릿 편집은 기획/운영, 매핑 변경은 시스템 관리자, 발송 이력은 CS/관제가 본다.

### 4.1 `/mail/templates` — 메일 템플릿 관리

```
[전역 PageHeader: 메일 템플릿 관리 / 홈 > 메일 관리 > …]   ← Layout 이 렌더. 페이지에서 중복 생성 금지
┌ b2b-toolbar ────────────────────────────────────────────────────────────┐
│ [검색] [카테고리 v] [상태 v]            [새 템플릿] [테스트 발송] [저장] │
└─────────────────────────────────────────────────────────────────────────┘
┌ 템플릿 (8) ─┬ 주문 확인 안내  ORDER_CONFIRM_KO [VELOCITY][v3] ORDER.CONFIRM ┐
│ ORDER_CON.. │                                   [미리보기][편집][버전]      │
│ 주문 확인.. │ [PC][모바일][텍스트]  [NexHub] 주문이 접수되었습니다 (…)      │
│ ─────────── │ ┌───────────────────────────────────────┐                    │
│ USER_WELC.. │ │  iframe sandbox 렌더 (샘플값 주입)     │                    │
│ 가입 환영.. │ └───────────────────────────────────────┘                    │
└─────────────┴───────────────────────────────────────────────────────────────┘
```

- **좌측(260px) [목록]**: 템플릿명 · 상태 뱃지 · (카테고리 · 버전). **`TEMPLATE_CODE` 는 노출하지 않는다.**
  검색/카테고리/상태 필터는 툴바로 올린다.
- **우측 헤더 한 줄**: 이름 · 엔진 · 현재 버전 · **연결된 발송 이벤트**.
  이벤트가 없으면 빨간 경고 — 아무 데서도 안 쓰는 템플릿이라는 뜻.
- **미리보기 탭**: `iframe srcdoc` + `sandbox` 로 격리. 페이지 CSS 가 메일 HTML 을 오염시키지 않게 한다.
  PC(600px) / 모바일(375px) / 텍스트(BODY_TEXT). 필수 변수 누락 시 상단 한 줄 경고.
- **편집 탭**: 상단 **템플릿 정보**(이름·코드·카테고리·엔진·상태·설명) →
  제목/프리헤더/HTML본문/텍스트본문 → 변경사유. 우측에 `MAIL_TEMPLATE_VAR` 표.
  변수명 클릭 → 커서 위치에 `${var}` 삽입. 샘플값·엔진 변경 → 미리보기 즉시 반영.
  코드 입력란은 `DRAFT` 가 아니면 잠기고, 저장 시 대문자 정규화 + 중복 검사한다.
  [새 템플릿] 을 누르면 편집 탭이 열리며 **템플릿명 입력란에 포커스**가 간다.
- **버전 탭**: 목록 + **[보기](읽기 전용 열람)** / **[되돌리기](실제 롤백)**. §2.5 참조.

#### `TEMPLATE_CODE` 를 화면에 노출하지 않는 이유

`MAIL_EVENT_TEMPLATE` 는 `TEMPLATE_CODE` 가 아니라 **`TEMPLATE_ID`(FK)** 로 템플릿을 참조한다.
즉 코드는 **아무 로직도 참조하지 않는 유니크 제약**이며, 운영자가 목록에서 볼 이유가 없다.
용도는 두 가지뿐이다 — ① `.vm` 파일 → DB seed 시 매칭 키, ② 장애 로그 추적.

따라서 코드는 **편집 탭의 [템플릿 코드] 입력란 한 곳에서만** 관리하고,
목록·헤더·매핑 현황·발송 이력은 전부 **템플릿명**으로 표시한다(코드는 `title` 툴팁으로만 남긴다).
운영자는 이름으로 찾고, 개발자는 필요할 때 툴팁·편집 탭에서 확인한다.
- **테스트 발송 모달**: 좌 변수 폼(자동 생성) / 우 실시간 렌더.

### 4.2 `/mail/dispatch-map` — 발송 매핑 현황

`MAIL_EVENT` 를 기준(LEFT JOIN)으로 조회하므로 **템플릿이 안 붙은 발송 지점까지 빠짐없이 드러난다.**
툴바 우측 한 줄 요약: `이벤트 12 · 정상 8 · 미매핑 2 · 비활성 2 | 30일 발송 18 / 실패 3`.
본문은 모듈(USER/ORDER/APPROVAL/NOTICE/MARKETING)별 그룹 행을 낀 단일 테이블 하나.

| 바인딩 상태 | 표시 | 의미 |
|---|---|---|
| `OK` | 초록 dot | 활성 템플릿 + TO 수신자 규칙이 모두 있음 |
| `UNMAPPED` | 빨강 dot | 템플릿 미연결 = **발송 시 터지는 지점** |
| `NO_RECIPIENT` | 빨강 dot | 템플릿은 있으나 **TO 수신자 규칙이 없어 발송 대상을 못 찾음** |
| `INACTIVE` | 주황 dot | DRAFT/ARCHIVED 템플릿에 연결됨 |

`문제 항목만` 체크박스로 정상 외 항목만 걸러 본다.

**행을 클릭하면 우측에 발송 설정 패널이 열린다.** 이 화면이 "코드 수정 없이 메일을 갈아끼우는" 실제 지점이다.

```
1. 무엇을 보낼지  MAIL_EVENT_TEMPLATE
   연결 템플릿 select (카테고리별 optgroup) · 발신자명 · 발신/회신 주소 · 적용 시작일
   선택 즉시 엔진·버전 배지와 제목 미리보기가 갱신된다

2. 누구에게 보낼지  MAIL_EVENT_RECIPIENT
   [구분 TO/CC/BCC] [수신자 유형] [대상값 / 조건식] [삭제]   + 규칙 추가
   대상값이 필요한 유형(TEAM/ROLE/FIXED/EXPRESSION)만 입력란이 열린다

3. 발송 요약
   제목 / 발신 / 받는사람 / 참조 / 숨은참조 를 저장 전에 확인
   TO 가 비어 있으면 빨갛게 "없음 (발송 실패)"
```

저장 시 검증 — 대상값이 필요한 유형인데 비어 있거나, 템플릿을 연결했는데 발신 주소가 없으면 중단한다.

### 4.3 `/mail/send-log` — 발송 이력

필터(유형/상태/템플릿/수신자) + 목록 + 우측 상세 패널.
상세에는 치환 데이터 JSON, 오류 코드/메시지, 그리고 **`VERSION_ID` + `MERGE_DATA_JSON` 으로 재현한 발송 본문**.
`FAILED`/`BOUNCED` 만 재발송 버튼 활성.

## 5. DDL 스키마

8 테이블 + 조회 뷰 1개.

| 테이블 | 역할 |
|---|---|
| `MAIL_TEMPLATE_LAYOUT` | 공통 헤더/푸터/기본 CSS. CI·법적고지 변경 시 한 행만 고치면 전체 반영 |
| `MAIL_TEMPLATE` | 마스터 (코드/카테고리/`ENGINE_TYPE`/`LOCALE_CODE`/상태/`CURRENT_VERSION_ID`) |
| `MAIL_TEMPLATE_VERSION` | 본문 버전 이력 (SUBJECT / BODY_HTML / BODY_TEXT). **수정 = 새 행 INSERT** |
| `MAIL_TEMPLATE_VAR` | 변수 정의 (타입/필수/샘플값) → 테스트 폼 자동생성 + 발송 전 검증 |
| `MAIL_TEMPLATE_ATTACH` | 고정 첨부 및 인라인 이미지(CID) |
| `MAIL_EVENT` | 발송 지점 정의 (`ORDER.CONFIRM` 등). 코드가 참조하는 불변 키 |
| `MAIL_EVENT_TEMPLATE` | **이벤트 ↔ 템플릿 바인딩** — 무엇을 보낼지 (locale/brand/유효기간별) |
| `MAIL_EVENT_RECIPIENT` | **수신자 결정 규칙** — 누구에게 보낼지 (TO/CC/BCC · 조건부) |
| `MAIL_SEND_LOG` | 발송 이력 (`VERSION_ID` 스냅샷 / `MERGE_DATA_JSON` / 상태 / 오픈·클릭) |
| `V_MAIL_DISPATCH_MAP` | 매핑 현황 화면 조회 뷰 (`MAIL_EVENT` 기준 LEFT JOIN) |

### 왜 이렇게 쪼갰나

- **VERSION 분리** — 본문을 마스터에 두면 이력이 사라진다. "누가 언제 뭘 바꿨고 되돌릴 수 있나"가 감사 요건.
- **EVENT ↔ TEMPLATE 분리** — 이벤트는 코드가 참조하는 불변 키, 템플릿은 갈아끼우는 대상.
  둘을 합치면 템플릿 교체 시 코드 수정이 필요해진다. 분리해야 무중단 문구 교체가 성립한다.
- **RECIPIENT 분리** — "무엇을"과 "누구에게"는 바뀌는 주기가 다르다. 수신자가 더 자주 바뀐다.
  이걸 코드에 두면 템플릿을 DB 로 뺀 의미가 절반으로 준다.
- **VAR 테이블** — 본문에서 정규식으로 변수를 긁으면 타입·필수·설명을 알 수 없다.
  명시 정의가 있어야 테스트 폼 자동생성과 발송 전 검증이 가능하다.
- **LOG 에 VERSION_ID** — 사후 재현성. §2.2 8단계 참조.
- **LAYOUT 분리** — 템플릿 20개에 푸터 법적고지가 복붙돼 있으면 법무 문구 변경 시 20번 수정한다.

### 운영 시 주의

- `MAIL_SEND_LOG` 는 `REQ_DT` 기준 RANGE 파티셔닝. 90일 경과분은 `BODY_SNAP` 을 NULL 처리하는 배치 권장.
- `MAIL_TEMPLATE` ↔ `MAIL_TEMPLATE_VERSION` 은 순환 FK 이므로 `CURRENT_VERSION_ID` FK 는 테이블 생성 후 `ALTER` 로 추가.

## 6. 백엔드 구현 가이드

### 6.1 두 가지 렌더 방식 — 용도가 다르다

**(A) `evaluate()` — 매번 파싱. 미리보기 / 테스트 발송용**

```java
String templateBody = version.getBodyHtml();   // DB CLOB 에서 읽은 Velocity HTML

VelocityContext context = new VelocityContext(model);
context.put("esc", new EscapeTool());          // ${esc.html($userName)} XSS 차단

StringWriter writer = new StringWriter();
velocityEngine.evaluate(context, writer, "mailRender", templateBody);
String finalHtml = writer.toString();
```

**(B) `StringResourceLoader` — 파싱 결과 캐싱. 대량 발송용**

`evaluate()` 는 호출마다 문자열을 다시 파싱한다. 뉴스레터 1만 건이면 1만 번 파싱이므로 캐시를 쓴다.

```java
// 부팅 시 1회
VelocityEngine engine = new VelocityEngine();
engine.setProperty(RuntimeConstants.RESOURCE_LOADERS, "string");
engine.setProperty("resource.loader.string.class", StringResourceLoader.class.getName());
engine.setProperty("resource.loader.string.repository.static", "false");
engine.init();

// 버전 활성화 시 등록 — 키를 VERSION_ID 로 잡으면 버전이 바뀌는 순간 키가 바뀌어 캐시 무효화가 자동
StringResourceLoader.getRepository()
    .putStringResource("mail_" + version.getVersionId(), version.getBodyHtml());

// 발송 시 — 파싱된 Template 재사용
Template tpl = engine.getTemplate("mail_" + version.getVersionId(), "UTF-8");
tpl.merge(context, writer);
```

### 6.2 엔진 분기

`ENGINE_TYPE` 컬럼으로 템플릿 단위 선택. 레거시 `.vm` 자산을 이관하면서 신규는 Thymeleaf 로 갈 수 있다.

```java
String rendered = switch (version.getEngineType()) {
    case "VELOCITY"  -> velocityRender(version, model);                 // evaluate / StringResourceLoader
    case "THYMELEAF" -> springTemplateEngine.process(body, thymeCtx);   // StringTemplateResolver
    case "PLAIN"     -> simpleReplace(body, model);                     // ${var} 단순 치환
    default -> throw new IllegalStateException("unknown engine: " + version.getEngineType());
};
```

| 상황 | 권장 |
|---|---|
| 기존 `.vm` 자산이 많다 | **Velocity** — `velocity-engine-core` 직접 의존. Spring Boot 3 는 Velocity 자동설정이 없으므로 `VelocityEngine` 을 `@Bean` 직접 등록 |
| 신규 구축 / Spring Boot 3 | **Thymeleaf** — 공식 스타터, `StringTemplateResolver` 로 DB 문자열 렌더 |
| 단순 안내메일 | `PLAIN` — 엔진 의존 없음 |

### 6.3 발송 서비스 골격

```java
@Service
@RequiredArgsConstructor
public class MailDispatchService {

    private final MailTemplateRepository templateRepo;
    private final MailVariableRepository varRepo;
    private final MailSendLogRepository logRepo;
    private final MailRenderService renderService;         // §6.1~6.2
    private final MailRecipientResolver recipientResolver;  // MAIL_EVENT_RECIPIENT 해석
    private final JavaMailSender mailSender;

    @Transactional
    public void send(String eventCode, Map<String, Object> model) {
        // 1. 이벤트 → 활성 매핑 → 템플릿 → 현재 버전
        var binding = templateRepo.findActiveBinding(eventCode, localeOf(model), brandOf(model))
                .orElseThrow(() -> new MailNotMappedException(eventCode));
        var version = binding.getTemplate().getCurrentVersion();

        // 2. 수신자 결정 — MAIL_EVENT_RECIPIENT 규칙 해석
        var addresses = recipientResolver.resolve(binding.getEventId(), model);
        if (addresses.to().isEmpty()) {
            logRepo.save(MailSendLog.failed(binding, version, null, "NO_RECIPIENT", "TO 수신자 없음", model));
            throw new MailNoRecipientException(eventCode);
        }

        // 3. 필수 변수 검증 — 깨진 메일을 보내느니 안 보낸다
        var missing = varRepo.findRequired(version.getTemplateId()).stream()
                .map(MailTemplateVar::getVarName)
                .filter(name -> !model.containsKey(name))
                .toList();
        if (!missing.isEmpty()) {
            logRepo.save(MailSendLog.failed(binding, version, to, "VAR_MISSING", missing.toString(), model));
            throw new MailVariableMissingException(missing);
        }

        // 3. 레이아웃 결합 + 엔진 머지
        var layout  = binding.getTemplate().getLayout();
        var html    = renderService.render(layout.wrap(version.getBodyHtml()), model, version.getEngineType());
        var subject = renderService.render(version.getSubject(),  model, version.getEngineType());
        var text    = renderService.render(version.getBodyText(), model, version.getEngineType());

        // 4. multipart/alternative 조립 + CSS 인라이닝
        MimeMessage message = mailSender.createMimeMessage();
        var helper = new MimeMessageHelper(message, true, "UTF-8");
        helper.setFrom(binding.getFromEmail(), binding.getFromName());
        helper.setTo(addresses.to().toArray(String[]::new));
        if (!addresses.cc().isEmpty())  helper.setCc(addresses.cc().toArray(String[]::new));
        if (!addresses.bcc().isEmpty()) helper.setBcc(addresses.bcc().toArray(String[]::new));
        helper.setSubject(subject);
        helper.setText(text, cssInliner.inline(html));   // (plain, html) 순서
        mailSender.send(message);

        // 5. VERSION_ID 스냅샷으로 감사 로그
        logRepo.save(MailSendLog.sent(binding, version, addresses, subject, model, message.getMessageID()));
    }
}
```

### 6.4 보안

- 템플릿 저장 시 서버에서 sanitize — `<script>`, `on*=`, `javascript:` 제거.
- 미리보기 iframe 은 `sandbox` 속성으로 스크립트 차단.
- 치환 값은 HTML 이스케이프 (`$esc.html($userName)` 또는 서버측 escape).
- 테스트 발송 수신자는 사내 도메인 화이트리스트로 제한.

### 6.5 HTML 메일 작성 제약

- 레이아웃은 `<table>` 기반. flex/grid 는 Outlook(Word 렌더링 엔진)에서 무시된다.
- CSS 는 인라인 style 우선. `<style>` 블록은 일부 클라이언트가 제거한다.
- 이미지는 반드시 `alt` + 절대경로 URL 또는 인라인 CID.
- 최대 폭 600px 고정. 웹폰트 금지(system font stack).
- 다크모드: 배경/글자색을 **둘 다** 명시. 배경만 지정하면 클라이언트가 글자색을 반전시켜 안 보인다.

## 9. 다른 프로젝트 AI 지시용 프롬프트

```markdown
[역할]
너는 엔터프라이즈 B2B 어드민 전문 시니어 풀스택 엔지니어다.

[구축 대상]
B2B 메일 템플릿 관리 시스템 — 화면 3종 + DDL. (DB 연동은 다음 단계, 지금은 목데이터)

[아키텍처 원칙 — 반드시 준수]
1. 템플릿 본문은 디스크의 .vm 파일이 아니라 DB CLOB(BODY_HTML)에 Velocity 문법 HTML 로 저장한다.
   런타임은 velocityEngine.evaluate() 또는 StringResourceLoader 로 문자열을 머지한다.
   이유: 다중 WAS 파일 동기화 불가 / 무중단 문구 교체 / 원클릭 롤백.
2. 본문 수정은 UPDATE 가 아니라 MAIL_TEMPLATE_VERSION 에 새 행 INSERT 다.
   마스터는 CURRENT_VERSION_ID 로 활성 버전만 가리킨다.
3. 발송 로그에는 TEMPLATE_ID 가 아니라 VERSION_ID 를 남긴다 (발송 당시 원문 재현).
4. 코드는 MAIL_EVENT.EVENT_CODE 만 참조한다. 템플릿 교체는 MAIL_EVENT_TEMPLATE 에서 하며
   소스 수정·재배포가 필요 없어야 한다.
5. 변수는 MAIL_TEMPLATE_VAR 에 명시 정의한다. 이 정의로 테스트 발송 폼을 자동 생성하고,
   REQUIRED='Y' 인데 값이 없으면 발송을 중단한다.

[화면 3종]
- /mail/templates    : 좌 목록(260px) + 우 3탭(미리보기/편집/버전) + 테스트발송 모달
- /mail/dispatch-map : MAIL_EVENT 기준 LEFT JOIN 으로 미매핑 발송 지점까지 노출
- /mail/send-log     : 발송 이력 + VERSION_ID 로 원문 재현 + 재발송

[UI 규칙]
1. 고밀도 B2B: 본문 13px, 메타 11~12px, 폼/버튼 높이 28~30px. B2C용 큰 폰트 금지.
2. 상위 Layout 이 이미 제목·브레드크럼을 렌더하면 페이지에서 h1/h4 를 중복 생성하지 않는다.
3. 프로젝트 공통 CSS 토큰만 사용하고 색상 hex 를 하드코딩하지 않는다 (다크모드 자동 대응).
4. 화면에 학습용 설명 배너·체크리스트·요약 카드 남발 금지. 요약은 툴바 한 줄로.
5. 미리보기는 iframe + sandbox 로 격리한다 (페이지 CSS 가 메일 HTML 을 오염시키지 않게).

[산출물]
- MySQL / Oracle DDL + 시드 SQL
- 화면 3종 (목데이터 동작)
- 백엔드 연동 지점을 주석으로 명시한 렌더링 유틸
```
